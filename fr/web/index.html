Documentation d'implémentation

CGS SDK

Le kit de développement pour intégrer le contenu Cafeyn — articles, magazines et éditions — dans n'importe quel produit web : authentification, catalogue de contenu, composants prêts à l'emploi et moteurs de lecture embarquables.

core 0.1.4 articlereader 1.0.0-alpha.1 pdfreader 1.0.0-alpha3 react · vue · vanilla 0.1.0
Introduction

Vue d'ensemble

CGS (Content & General Services) est organisé en six packages du monorepo web-cgs, chacun avec une responsabilité précise.

Le SDK s'utilise à deux niveaux :

  • Le cœur (core) — une classe CGS unique qui gère l'authentification et expose l'API de contenu (articles, éditions, publications, médias, vidéos). Elle est utilisée par tous les autres packages et peut aussi être consommée directement.
  • Les librairies de composants (react, vue, vanilla) — un même catalogue de 9 composants (blocs, cellules, en-têtes, lecteurs) implémenté dans les trois écosystèmes avec la même API de props.

Deux moteurs de lecture spécialisés, articlereader et pdfreader, sont packagés indépendamment (Svelte, compilés en scripts autonomes) et embarqués par les composants ArticleReader / PDFReader — ou utilisables directement, sans framework.

Démarrage

Getting started

Quatre étapes pour afficher votre premier composant. Chaque bloc de code ci-dessous propose un onglet par framework.

1. Installation

Dans un projet React ou Vue existant, ajoutez la librairie de composants CGS, le core, et les deux moteurs de lecture (nécessaires en peer dependency dès que vous utilisez ArticleReader ou PDFReader) — le framework lui-même est déjà dans vos dépendances.

terminal
pnpm add @lekiosquefr/web-cgs-react @lekiosquefr/web-cgs-core \
         @lekiosquefr/web-cgs-articlereader @lekiosquefr/web-cgs-pdfreader
terminal
pnpm add @lekiosquefr/web-cgs-vue @lekiosquefr/web-cgs-core \
         @lekiosquefr/web-cgs-articlereader @lekiosquefr/web-cgs-pdfreader
index.html
<!-- pas d'installation npm : la librairie vanilla est distribuée en scripts prêts à l'emploi -->
<link rel="stylesheet" href="/cgs/core/index.css">
<script src="/cgs/core/index.iife.js"></script>  <!-- expose window.CGS -->

<link rel="stylesheet" href="/cgs/components/index.css">
<script src="/cgs/components/index.js"></script>  <!-- expose window.CGSComponents -->

2. Initialisation

Créez une instance CGS avec votre clé de licence. À ce stade, aucune notion d'utilisateur n'entre en jeu — c'est uniquement ce qui identifie votre application auprès de l'API Cafeyn.

main.tsx
import { CGSProvider } from "@lekiosquefr/web-cgs-react";
import "@lekiosquefr/web-cgs-react/dist/index.css";
import ReactDOM from "react-dom/client";
import App from "./App";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <CGSProvider licenseKey="YOUR_LICENSE_KEY">
    <App />
  </CGSProvider>,
);
main.ts
import { createCgs } from "@lekiosquefr/web-cgs-vue";
import "@lekiosquefr/web-cgs-vue/dist/index.css";
import { createApp } from "vue";
import App from "./App.vue";

const app = createApp(App);

app.use(createCgs({ licenseKey: "YOUR_LICENSE_KEY", env: "production" }));
app.mount("#app");
index.html
<script>
  document.addEventListener("DOMContentLoaded", () => {
    window.cgsComponents = new CGSComponents("YOUR_LICENSE_KEY");
  });
</script>
i

env est optionnel partout (défaut "production"), sauf pour createCgs (Vue) : son type le rend obligatoire, même si CGS retombe sur "production" en interne.

3. Authentification

CGS ne gère pas lui-même la connexion de l'utilisateur : c'est votre application qui authentifie la personne (identifiants, SSO…) auprès de votre propre backend, puis transmet le token obtenu à CGS pour ouvrir une session.

  1. Votre backend authentifie l'utilisateur

    Formulaire, SSO, etc. — géré entièrement par votre application. Vous en récupérez un token externe.

  2. Le token est transmis à CGS

    CGS.auth.validate(externalToken) échange ce token contre une session CGS (access & refresh token, persistés en cookies).

  3. Le résultat se lit comme un booléen

    La promesse résout true ou false — elle ne lève jamais d'exception pour un échec d'échange. false signifie un token invalide ou expiré : c'est à votre application de réagir (écran de connexion, nouvelle tentative…).

App.tsx
import { Context } from "@lekiosquefr/web-cgs-react";
import { useContext, useEffect, useState } from "react";

export default function App() {
  const CGS = useContext(Context);
  const [authFailed, setAuthFailed] = useState(false);

  useEffect(() => {
    async function authenticate() {
      // externalToken provient de VOTRE backend d'authentification
      const success = await CGS.auth.validate(externalToken);
      if (!success) setAuthFailed(true);
    }
    authenticate();
  }, []);

  if (authFailed) return <LoginScreen />;
  return <main>…</main>;
}
App.vue
<script setup lang="ts">
import { useCgs } from "@lekiosquefr/web-cgs-vue";
import { onMounted, ref } from "vue";

const CGS = useCgs();
const authFailed = ref(false);

onMounted(async () => {
  // externalToken provient de VOTRE backend d'authentification
  const success = await CGS.auth.validate(externalToken);
  if (!success) authFailed.value = true;
});
</script>

<template>
  <LoginScreen v-if="authFailed" />
</template>
index.html
<script>
  document.addEventListener("DOMContentLoaded", async () => {
    // externalToken provient de VOTRE backend d'authentification
    const success = await cgsComponents.core.auth.validate(externalToken);
    if (!success) {
      window.location.href = "/login";
    }
  });
</script>
!

Ne codez jamais en dur une clé de licence ou un token dans un dépôt public. Les exemples ci-dessus utilisent des espaces réservés — injectez ces valeurs via votre configuration d'environnement ou votre flux d'authentification.

Core SDK

La classe CGS

Le point d'entrée unique de @lekiosquefr/web-cgs-core : une instance par application, injectée dans les composants ou utilisée directement. Identique quel que soit le framework choisi.

core
class CGS {
  constructor(licenseKey: string, env: Env = "production")

  auth: Auth
  articles: Articles
  issues: Issues
  publications: Publications
  medias: Medias
  videos: Videos
  reader: Reader
}

type Env = "development" | "staging" | "preprod" | "production";

Toutes les ressources de contenu suivent le même schéma : get{X}(id) pour un élément unique, get{X}s(filter, orderBy?, paging?) pour une recherche paginée.

Voir Getting started → Authentification pour la marche à suivre complète et la gestion des erreurs.

Reader tickets

Le module reader délivre un ticket de lecture pour une édition — c'est le mécanisme utilisé en interne par PDFReader (voir son schéma de fonctionnement) pour charger les pages, les articles et les enrichissements d'un numéro. Vous pouvez aussi l'appeler directement si vous construisez votre propre affichage.

MéthodeRetourDescription
getTicket(issueId)Promise<Ticket>Ouvre une session de lecture pour une édition.
getArticles(ticket)Promise<Article[]>Articles disponibles dans l'édition — à n'appeler que si ticket.hasArticles est vrai.
getEnrichments(ticket)Promise<Box[]>Zones interactives ("boxes") positionnées sur les pages — à n'appeler que si ticket.hasEnrichment est vrai.
getTiles(ticket)Promise<TilesReaderInfo>Tuiles d'images des pages, pour l'affichage progressif du magazine.

ticket ci-dessus désigne toujours la chaîne Ticket.ticket (pas l'objet entier) — voir sa forme complète ci-dessous.

Exemple — flux complet d'ouverture d'une édition
const ticket = await CGS.reader.getTicket("17");

if (!ticket) {
  // édition introuvable, ou accès refusé pour cet utilisateur
  return;
}

// toujours disponible : les tuiles de page
const tiles = await CGS.reader.getTiles(ticket.ticket);

// conditionnels : à ne demander que si l'édition les propose
const articles = ticket.hasArticles
  ? await CGS.reader.getArticles(ticket.ticket)
  : [];

const enrichments = ticket.hasEnrichment
  ? await CGS.reader.getEnrichments(ticket.ticket)
  : [];

Sous le capot

Quel que soit le framework, ArticleReader ne fait qu'appeler l'API impérative du package articlereader sur un <div> qu'il monte lui-même.

MéthodeDescription
init(config)Monte le lecteur. Requiert target, cgsInstance et articleIds.
updateArticles(articleIds)Remplace la liste d'articles navigables sans démonter le lecteur.
destroy()Démonte le lecteur et réinitialise son état interne.
  1. Vous fournissez une liste d'identifiants

    articleIds définit les articles que la personne peut parcourir, dans l'ordre donné.

  2. Chaque article est chargé à la demande

    Le lecteur appelle core.articles.getArticle(articleId) pour l'article affiché — pas de préchargement global.

  3. La liste peut évoluer sans redémonter le lecteur

    updateArticles() met à jour articleIds à chaud (utile pour une recherche ou une pagination pendant la lecture).

pdfreader déclare articlereader en peer dependency : il l'embarque pour ouvrir un article directement depuis une page du magazine. Installez toujours les deux packages ensemble.

Sous le capot

PDFReader appelle l'API impérative du package pdfreader sur un <div> qu'il monte lui-même — même principe qu'ArticleReader, mais sans équivalent à updateArticles().

MéthodeDescription
init(config)Monte le lecteur. Requiert target, cgsInstance et issueId.
destroy()Démonte le lecteur et réinitialise son état interne.
i

Pour ouvrir une autre édition, il faut destroy() puis init() avec un nouvel issueId — contrairement à ArticleReader, la liste de contenu ne se met pas à jour à chaud.

  1. Ouverture d'un ticket de lecture

    init() appelle core.reader.getTicket(issueId) pour ouvrir une session de lecture sur l'édition.

  2. Chargement du contenu du ticket

    Le lecteur charge ensuite les tuiles de page (getTiles), et si l'édition en propose, les articles internes (getArticles) et les enrichissements interactifs (getEnrichments).

  3. Ouverture d'un article depuis une page

    Quand la personne tape sur un article du magazine, pdfreader réutilise en interne le package articlereader (Article.init()) pour l'afficher en plein écran.
