Implementation guide

CGS SDK

The development kit for integrating Cafeyn content — articles, magazines and issues — into any web product: authentication, content catalog, ready-to-use components and embeddable reading engines.

core 0.1.4 articlereader 1.0.0-alpha.1 pdfreader 1.0.0-alpha3 react · vue · vanilla 0.1.0
Introduction

Overview

CGS (Content & General Services) is organized into six packages in the web-cgs monorepo, each with a specific responsibility.

The SDK can be used at two levels:

  • The core (core) — a single CGS class that handles authentication and exposes the content API (articles, issues, publications, media, videos). It is used by all the other packages and can also be consumed directly.
  • The component libraries (react, vue, vanilla) — the same catalog of 9 components (blocks, cells, headers, readers) implemented in all three ecosystems with the same props API.

Two specialized reading engines, articlereader and pdfreader, are packaged independently (Svelte, compiled into standalone scripts) and embedded by the ArticleReader / PDFReader components — or usable directly, without a framework.

Quick start

Getting started

Four steps to display your first component. Each code block below has one tab per framework.

1. Installation

In an existing React or Vue project, add the CGS component library, the core, and the two reading engines (required as peer dependencies as soon as you use ArticleReader or PDFReader) — the framework itself is already in your dependencies.

2. Initialization

Create a CGS instance with your license key. At this stage, no user is involved — the key only identifies your application to the Cafeyn API.

main.tsx
import { CGSProvider } from "@lekiosquefr/web-cgs-react";
import "@lekiosquefr/web-cgs-react/dist/index.css";
import ReactDOM from "react-dom/client";
import App from "./App";

ReactDOM.createRoot(document.getElementById("root")!).render(
  <CGSProvider licenseKey="YOUR_LICENSE_KEY">
    <App />
  </CGSProvider>,
);
main.ts
import { createCgs } from "@lekiosquefr/web-cgs-vue";
import "@lekiosquefr/web-cgs-vue/dist/index.css";
import { createApp } from "vue";
import App from "./App.vue";

const app = createApp(App);

app.use(createCgs({ licenseKey: "YOUR_LICENSE_KEY", env: "production" }));
app.mount("#app");
index.html
<script>
  document.addEventListener("DOMContentLoaded", () => {
    window.cgsComponents = new CGSComponents("YOUR_LICENSE_KEY");
  });
</script>
i

env is optional everywhere (default "production"), except for createCgs (Vue): its type makes it required, even though CGS falls back to "production" internally.

3. Authentication

CGS does not handle user sign-in itself: your application authenticates the user (credentials, SSO…) against your own backend, then passes the resulting token to CGS to open a session.

  1. Your backend authenticates the user

    Form, SSO, etc. — handled entirely by your application. You get back an external token.

  2. The token is passed to CGS

    CGS.auth.validate(externalToken) exchanges this token for a CGS session (access & refresh tokens, persisted in cookies).

  3. The result is read as a boolean

    The promise resolves to true or false — it never throws on a failed exchange. false means an invalid or expired token: it is up to your application to react (login screen, retry…).

App.tsx
import { Context } from "@lekiosquefr/web-cgs-react";
import { useContext, useEffect, useState } from "react";

export default function App() {
  const CGS = useContext(Context);
  const [authFailed, setAuthFailed] = useState(false);

  useEffect(() => {
    async function authenticate() {
      // externalToken comes from YOUR authentication backend
      const success = await CGS.auth.validate(externalToken);
      if (!success) setAuthFailed(true);
    }
    authenticate();
  }, []);

  if (authFailed) return <LoginScreen />;
  return <main>…</main>;
}
App.vue
<script setup lang="ts">
import { useCgs } from "@lekiosquefr/web-cgs-vue";
import { onMounted, ref } from "vue";

const CGS = useCgs();
const authFailed = ref(false);

onMounted(async () => {
  // externalToken comes from YOUR authentication backend
  const success = await CGS.auth.validate(externalToken);
  if (!success) authFailed.value = true;
});
</script>

<template>
  <LoginScreen v-if="authFailed" />
</template>
index.html
<script>
  document.addEventListener("DOMContentLoaded", async () => {
    // externalToken comes from YOUR authentication backend
    const success = await cgsComponents.core.auth.validate(externalToken);
    if (!success) {
      window.location.href = "/login";
    }
  });
</script>
!

Never hard-code a license key or a token in a public repository. The examples above use placeholders — inject these values through your environment configuration or your authentication flow.

Core SDK

The CGS class

The single entry point of @lekiosquefr/web-cgs-core: one instance per application, injected into the components or used directly. Identical whichever framework you choose.

core
class CGS {
  constructor(licenseKey: string, env: Env = "production")

  auth: Auth
  articles: Articles
  issues: Issues
  publications: Publications
  medias: Medias
  videos: Videos
  reader: Reader
}

type Env = "development" | "staging" | "preprod" | "production";

All content resources follow the same pattern: get{X}(id) for a single item, get{X}s(filter, orderBy?, paging?) for a paginated search.

Auth

See Getting started → Authentication for the complete walkthrough and error handling.

MethodReturnsDescription
validate(externalToken)Promise<boolean>Exchanges an external token (issued by your backend) for a CGS session; persists the tokens in cookies.
refresh()Promise<boolean>Refreshes the session using the stored refresh token. Called automatically by the SDK on a 401 response.
logout()voidClears the local session (cookies + in-memory state).

Reader tickets

The reader module issues a reading ticket for an issue — this is the mechanism used internally by PDFReader (see its how-it-works flow) to load an issue's pages, articles and enrichments. You can also call it directly if you are building your own display.

MethodReturnsDescription
getTicket(issueId)Promise<Ticket>Opens a reading session for an issue.
getArticles(ticket)Promise<Article[]>Articles available in the issue — only call this if ticket.hasArticles is true.
getEnrichments(ticket)Promise<Box[]>Interactive areas ("boxes") positioned on the pages — only call this if ticket.hasEnrichment is true.
getTiles(ticket)Promise<TilesReaderInfo>Page image tiles, for progressive rendering of the magazine.

ticket above always refers to the Ticket.ticket string (not the whole object) — see its full shape below.

Example — full flow for opening an issue
const ticket = await CGS.reader.getTicket("17");

if (!ticket) {
  // issue not found, or access denied for this user
  return;
}

// always available: the page tiles
const tiles = await CGS.reader.getTiles(ticket.ticket);

// conditional: only request them if the issue provides them
const articles = ticket.hasArticles
  ? await CGS.reader.getArticles(ticket.ticket)
  : [];

const enrichments = ticket.hasEnrichment
  ? await CGS.reader.getEnrichments(ticket.ticket)
  : [];

Under the hood

Whatever the framework, ArticleReader simply calls the imperative API of the articlereader package on a <div> that it mounts itself.

MethodDescription
init(config)Mounts the reader. Requires target, cgsInstance and articleIds.
updateArticles(articleIds)Replaces the list of navigable articles without unmounting the reader.
destroy()Unmounts the reader and resets its internal state.
  1. You provide a list of identifiers

    articleIds defines the articles the user can browse, in the given order.

  2. Each article is loaded on demand

    The reader calls core.articles.getArticle(articleId) for the displayed article — no global preloading.

  3. The list can change without remounting the reader

    updateArticles() updates articleIds on the fly (useful for search or pagination while reading).

pdfreader declares articlereader as a peer dependency: it embeds it to open an article directly from a magazine page. Always install both packages together.

Under the hood

PDFReader calls the imperative API of the pdfreader package on a <div> that it mounts itself — same principle as ArticleReader, but with no equivalent of updateArticles().

MethodDescription
init(config)Mounts the reader. Requires target, cgsInstance and issueId.
destroy()Unmounts the reader and resets its internal state.
i

To open another issue, you must call destroy() then init() with a new issueId — unlike ArticleReader, the content list cannot be updated on the fly.

  1. Opening a reading ticket

    init() calls core.reader.getTicket(issueId) to open a reading session on the issue.

  2. Loading the ticket's content

    The reader then loads the page tiles (getTiles) and, if the issue provides them, the embedded articles (getArticles) and the interactive enrichments (getEnrichments).

  3. Opening an article from a page

    When the user taps an article in the magazine, pdfreader internally reuses the articlereader package (Article.init()) to display it full screen.
